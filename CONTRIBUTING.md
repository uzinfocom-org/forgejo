# Contributing to forgejo

Thanks for your interest in improving `forgejo` — a Haskell library for building Forgejo bots. This document covers how to set up your environment, the conventions the codebase follows, and how to get a change merged.

## Getting set up

The project uses a Nix flake for a reproducible dev environment (GHC 9.12, HLS, fourmolu, hlint, cabal-fmt, and the various native deps the library links against — zlib, bzip2, libzip, libpq).

```sh
git clone https://github.com/uzinfocom-org/forgejo.git
cd forgejo
nix develop
```

This drops you into a shell with everything needed to build, format, and lint. If you don't use Nix, you'll need GHC 9.12.x, `cabal-install`, and the native libraries listed above available on your system, plus `fourmolu`, `cabal-fmt`, and `hlint` for formatting/linting.

Build and test with cabal as usual:

```sh
cabal build
cabal test
```

A `cabal-hoogle` and `ghcid` are also available in the dev shell for fast iteration.

## Project layout

- `src/Forgejo.hs`, `src/Forgejo/App.hs` — top-level entry points and app wiring
- `src/Forgejo/API/` — Servant API type definitions, one module per resource (Issue, PullRequest, Repository, Organization, CommitStatus, OrgMembers)
- `src/Forgejo/Methods/` — client functions built on top of the API types
- `src/Forgejo/Types/` — request/response data types mirroring the Forgejo (Gitea-compatible) REST API
- `src/Forgejo/Webhook.hs` — webhook payload handling
- `test/` — the `hspec`/`hspec-wai` test suite

When adding support for a new Forgejo API endpoint, the usual shape is: add/extend the relevant type(s) in `Forgejo.Types`, declare the route in the matching `Forgejo.API.*` module, and expose a client function in the matching `Forgejo.Methods.*` module. Keep the module you're touching consistent with its neighbors rather than introducing a new pattern.

## Code style

- Formatting is enforced by **fourmolu** (Haskell), **cabal-fmt** (the `.cabal` file), and **nixfmt** (`.nix` files), orchestrated via `treefmt`. Run `treefmt` (or `fourmolu -i` / `cabal-fmt -i` individually) before committing — a `pre-commit` hook is wired up through `git-hooks.nix` in the flake and will run this automatically once you've entered `nix develop` at least once.
- The library builds with `-Wall -Wunused-imports`; new code should be warning-clean.
- `default-extensions` are set project-wide in `forgejo.cabal` (`BlockArguments`, `DataKinds`, `DeriveAnyClass`, `DerivingStrategies`, `ImplicitParams`, `ImportQualifiedPost`, `LambdaCase`, `OverloadedRecordDot`, `RecordWildCards`). Prefer these over ad hoc per-file pragmas when the extension is already available project-wide.
- Favor honest types and total functions — avoid partial functions (`head`, `fromJust`, incomplete pattern matches) in library code.
- Run `hlint` and address its suggestions unless there's a good reason not to.

## AI/LLM policy

**PRs written or substantially generated by AI/LLM tools will not be accepted.**

- This covers code, commit messages, and PR descriptions that are pasted-in or lightly-edited model output. Standard editor autocomplete (LSP suggestions, snippet expansion) is fine — the line is whether you understand and could defend every line you're submitting, not what tool touched your keyboard.
- If you used an AI tool to research an idea, debug locally, or sanity-check an approach, and none of its output ended up in the diff, that's outside the scope of this policy.
- A PR that's clearly unreviewed AI output — doesn't match the surrounding code's idioms, or whose author can't explain a design choice when asked — will be closed. Repeated attempts may result in a block.

## Making a change

1. Fork the repo and create a branch off `main` for your change.
2. Keep commits focused — one logical change per commit, with a clear message describing *why*, not just *what*.
3. Make sure `cabal build`, `cabal test`, and `treefmt` all pass cleanly.
4. Update `CHANGELOG.md` under an "Unreleased" section if your change is user-facing (new endpoint support, behavior change, bug fix).
5. Open a pull request against `main` with a description of the change and, if it touches the public API surface, a short note on any migration impact.

## Reporting issues

When filing an issue, please include:

- The Forgejo/Gitea server version you're targeting, if relevant
- A minimal reproduction (the API call or bot code that triggers the problem)
- What you expected vs. what happened, including any error output
